How DispatchIQ Works

End-to-end walkthrough of the problem formulation, simulation design, technical stack, algorithms, and assumptions behind this static portfolio prototype.

1. The Problem

Consider an organization that manages a fleet of drivers picking up and delivering items across a metro area. Orders arrive throughout the day with varying urgency levels, handling requirements, and deadlines. Each order originates at a pickup location and contains one or more packages, each potentially going to a different destination. The simulator dispatches in epochs as orders arrive rather than handing either solver the full day upfront.

Why is this hard? This is a Vehicle Routing Problem with Pickup and Delivery (VRPPD) — NP-hard in the general case. The challenge has three layers:

  1. Assignment (who gets what): Match N drivers to M orders while respecting hard constraints (equipment, certifications, capacity, shift windows, deadlines) and minimizing total cost
  2. Pooling (can we batch?): Group compatible nearby orders for a single driver when detour cost is low. In this repo this is exploratory only, not part of active dispatch.
  3. Routing (in what order): Optimize each driver's multi-stop delivery sequence (per-driver TSP with precedence constraints: pickup before delivery)

A human dispatcher handles layer 1 reasonably well but can't simultaneously optimize across all three. Each individual decision looks good — send the nearest eligible driver — but the sequence of decisions is often globally suboptimal. Assigning Driver A to Order X might be locally rational, but it leaves no feasible option for the higher-priority Order Y in the same batch.

This simulator demonstrates that gap in a simplified but non-clairvoyant model: how much is lost by sequential human decision-making vs. Hungarian batch assignment under shared constraints.

2. Domain Model

The data model has a two-level structure: an Order represents a single pickup event at one location, containing one or more Packages, each with its own cargo type, temperature regime, and destination.

Cargo Types

Each cargo type has specific temperature handling requirements and deadline constraints:

Multi-Destination Pickups

A key structural feature: one pickup location may generate multiple packages going to different destinations. Example:

Package 1 (Standard) → Destination A
Package 2 (Fragile, refrigerated) → Destination B
Package 3 (Standard) → Destination C

Without optimization: 3 separate driver dispatches to the same pickup location.
With DispatchIQ: 1 driver, 1 pickup, optimized 3-stop delivery route. This is where the largest cost savings come from.

Driver Capabilities

Drivers are heterogeneous. Each has specific equipment and certifications that create hard constraints on which orders they can serve:

Specialized equipment (e.g., cryogenic-capable vehicles) is scarce. A key optimization challenge is avoiding over-qualification — assigning a high-capability driver to a standard-tier order, leaving no capable driver for the order that actually needs that equipment.

3. Hard Constraints

Every driver-order assignment is checked against six hard constraints. If any fails, the assignment is infeasible (cost = ∞ in the optimization):

Additionally, temperature compatibility is checked for pooled orders: items flagged "must not freeze" cannot share a vehicle with frozen or cryogenic items.

No external mapping API is used. All distances are computed mathematically from coordinates. A production system would integrate OSRM, Google Directions API, or Mapbox for real road network routing, turn-by-turn distance, and live traffic data.

No commercial VRP solver is used. The prototype uses scipy's Hungarian algorithm (optimal for bipartite assignment) paired with custom nearest-neighbor + 2-opt heuristics for route optimization. No database. Scenarios are held in memory for the session. A production system would persist to PostgreSQL or similar.

Zero build step. Frontend is vanilla HTML/CSS/JS with CDN dependencies. No React, no Webpack, no npm.

6. Algorithm 1: Smart Greedy (Competent Dispatcher)

This isn't a straw man — it represents what a good human dispatcher does, making reasonable decisions one order at a time:

What it does well:

  1. Sort orders by urgency (STAT first), then by deadline tightness within each tier
  2. Check all hard constraints (equipment, certifications, capacity, shift window)
  3. Score each eligible driver considering:
    • Distance (primary factor — the dispatcher looks at the map)
    • Deadline feasibility — heavily penalizes drivers who'd likely miss the deadline (+50 penalty if infeasible, +5 if <15 min slack)
    • Equipment match — penalizes over-qualification (+3 if 2+ levels above needed, +0.5 for 1 level above)
  4. Pick the best-scoring driver. Move to the next order.

Scoring formula: score = distance_km + deadline_penalty + equipment_penalty

Where it still falls short (inherent limitations of sequential decision-making):

  • No global view: Each assignment is locally rational but globally suboptimal. Assigning Driver A here might leave no feasible option for Order Y arriving 10 minutes later. A human can't hold all N×M possibilities in their head.
  • Equipment preference, not optimization: The dispatcher tries to match equipment levels, but under time pressure still makes suboptimal matches. The Hungarian solver finds the lowest-cost 1:1 assignment under the modeled cost matrix for each dispatch epoch.
  • No delivery route optimization: When an order has 3 packages going to 3 different destinations, the dispatcher sends the driver in the order the destinations appear. The Hungarian path uses nearest-neighbor + 2-opt to find a shorter delivery sequence.
  • No pooling: Every order gets its own dedicated driver. Two facilities 500m apart each get separate drivers, even though one trip could serve both.
  • Deadline slack isn't weighed against future demand: The dispatcher doesn't think "this Routine order has 3 hours of slack, so I should save this nearby driver for the STAT that's likely coming in 20 minutes."

7. Algorithm 2: Hungarian Batch Assignment

Uses scipy.optimize.linear_sum_assignment (the Hungarian/Kuhn-Munkres algorithm) to find the minimum-cost driver-to-order matching for this simplified 1:1 assignment model:

Step 1: Build Cost Matrix (Ndrivers × Morders)

Each cell C[i][j] represents the total cost of assigning driver i to order j. The cost function is a weighted combination:

ComponentWeightDescription
Distance to pickup× urgency multiplierSTAT=3x, Urgent=2x, Routine=1x, Standard=0.8x
Infeasibility106If any hard constraint is violated, cost is effectively infinite
Deadline risk10 per minuteProportional to minutes of negative slack (pessimistic estimate)
Shift overtime500Flat penalty if estimated completion exceeds shift end
Over-qualification5 per levelPenalizes wasting specialized equipment on orders that don't need it
Delivery route distance× 0.5Estimated multi-destination delivery distance (discounted)

Step 2: Solve

The Hungarian algorithm finds the assignment that minimizes total cost across all driver-order pairs simultaneously. It runs in O(n³) time and guarantees the global optimum for the linear assignment problem defined by the cost matrix. The matrix is padded to square if N ≠ M.

Step 3: Optimize Delivery Routes

For each assigned driver with multi-destination deliveries:

  1. Nearest-neighbor construction: Build an initial route visiting the closest unvisited stop, respecting pickup-before-delivery precedence
  2. 2-opt improvement: Iteratively reverse route segments to eliminate crossings, checking precedence constraints on each swap. Continues until no improving swap is found (up to 100 iterations).

8. Exploratory Pooling & Insertion Modules

This repo includes standalone pooling and insertion helpers for exploration, but they are not wired into the active dispatch path. The live demo still assigns at most one order per driver per dispatch epoch.

Order Pooling: The helper groups nearby compatible orders into batches before assignment. A driver picking up from Facility A can also service Facility B (0.5 km away) on the same trip.

Pooling Criteria

  • Pickup locations within 2 km of each other
  • Temperature-compatible cargo (items flagged "must not freeze" cannot ride with frozen items)
  • Combined package count fits within driver capacity
  • All orders in the batch can still meet their individual deadlines given the multi-stop route

Slack-Based Holding

Orders with sufficient slack can be held briefly, waiting for a pooling opportunity:

UrgencyHold TimeRationale
STAT0 minutesDispatch immediately, never hold
Urgent5 minutesShort hold, pool only if match already available
Routine20 minutesActively look for nearby orders to batch
Standard60 minutesMaximum pooling opportunity

That holding logic is conceptual here; the current API does not delay dispatch to wait for a pooling match.

Cheapest Insertion

In a future, richer event-driven system, a new order could be evaluated for insertion into an existing route vs. dispatching a new driver:

  1. For each active driver route, find the position that adds minimum extra distance for the new pickup + delivery stops
  2. Verify that insertion doesn't cause any existing order on that route to miss its deadline (cascade check)
  3. Compare best insertion cost vs. cost of dispatching a new idle driver
  4. If insertion is cheaper and feasible → insert; otherwise → new dispatch

9. Distance & Travel Time Model

The distance model is intentionally simplified for the prototype, with each simplification representing a known upgrade path:

Distance Calculation

  • Formula: road_distance = haversine(A, B) × 1.4
  • Haversine computes great-circle distance between two lat/lng coordinates using the WGS-84 earth radius (6,371 km)
  • Road factor of 1.4 accounts for the grid street layout vs. straight-line distance. For NYC's Manhattan grid, this is within ~15% of actual road distance. Suburban areas would need a higher factor (~1.6-1.8).
  • No routing API is called. OSRM, Google Directions, or Mapbox would provide actual road network distances, turn penalties, and one-way street routing.

Travel Time

  • Base speed: Cars 25 km/h, Vans 22 km/h, Bikes 18 km/h — reasonable NYC urban averages
  • Deterministic time: base_time = road_distance / speed × 60 (minutes)
  • Stochastic variability: Travel times are modeled as log-normal distributions around the base time. The log-normal is chosen because travel times are always positive, right-skewed (traffic jams create long tails), and multiplicative (delays compound).
    • Normal conditions: CV = 0.20 (coefficient of variation)
    • Rush hour: CV = 0.35
  • Pessimistic estimates: Deadline feasibility checks use the 80th percentile of the log-normal distribution, computed analytically via scipy.stats.norm.ppf(0.80). This means the algorithm builds routes that succeed 80% of the time, not just on average.

Stop Buffer Times

  • Pickup: 5 minutes (loading, paperwork, verification)
  • Delivery: 3 minutes per destination (unloading, handoff)
  • These are configurable constants, not learned from data

11. Roadmap

Key production upgrades, roughly in order of impact:

  1. Real routing API (OSRM / Google Directions): Replace Haversine approximation with actual road network distances, turn penalties, and one-way street routing
  2. Google OR-Tools VRP solver: Joint optimization of assignment + routing + pooling in a single model, replacing the current two-stage approach
  3. Real-time GPS integration: Live driver positions instead of simulated, with dynamic re-optimization as conditions change
  4. Live traffic data: Time-of-day speed profiles and real-time congestion from traffic APIs
  5. Predictive demand modeling: Learn arrival patterns from historical data — pre-position drivers for anticipated demand
  6. Soft constraint relaxation: Allow controlled deadline flexibility when it produces significantly better global outcomes
  7. Tracking and audit trail: Scan-based verification at pickup and delivery for full chain of custody
  8. Driver mobile app: Turn-by-turn navigation with optimized stop sequence, real-time notifications
